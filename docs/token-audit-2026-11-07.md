## 1. system prompt เปลี่ยนระหว่างเทิร์น ทำให้ prefix ทั้งก้อนต้องเขียนใหม่ (ประหยัดได้มากที่สุด)

**ที่พบ**
- `CodeAgentService.cs:1625–1657` ใส่ `- Git Status:` (`git status --short`) ไว้ใน `# Environment` ของ system prompt
  และ prompt ถูกสร้างใหม่ทุกเทิร์น (cache ภายในแอปมีอายุแค่ 30 วินาที, `CodeAgentService.cs:530–557`)
- harness วัดได้ว่า **แก้ไฟล์ที่ track อยู่เพียงไฟล์เดียว, สร้างไฟล์ใหม่ หรือ commit ก็ทำให้ system prompt เปลี่ยนทุกครั้ง**
  โดยจุดแรกที่เปลี่ยนอยู่ที่ตัวอักษรที่ 13,795 จาก 24,102
  เทิร์นที่มีการเขียนโค้ดจึงทำให้เทิร์นถัดไปต้องเขียนใหม่ทั้งหมด ทั้ง tools, system และประวัติทั้งหมด
- tools อยู่ก่อน system ใน request แต่ไม่มี `cache_control` ของตัวเอง (`AnthropicProvider.cs:115`, `:497`)
  จึงต้องเขียน tools ใหม่ด้วยทุกครั้งที่ system เปลี่ยน แม้ tools จะไม่ได้เปลี่ยนเลย
- ส่วนอื่นที่เปลี่ยนได้ระหว่างเทิร์น:
  - `BrainSyncService.cs:72` ใส่จำนวน tool ของ brain และ last error ลงในบรรทัด LIVE STATUS (`CodeAgentService.cs:1511`)
  - `ProjectToolModule.cs:471` เรียง Related projects ตามลำดับที่เปิดล่าสุด
  - `CodeAgentService.cs:1800/1813` PROJECT STRUCTURE และ CODEBASE MAP เปลี่ยนเมื่อมีไฟล์ใหม่
  - `CodeAgentService.cs:1894` memory index เปลี่ยนเมื่อมี memory_save
  - `CodeAgentService.cs:1615` Date เปลี่ยนวันละครั้ง

**ที่วัดได้จาก log**: ขั้นแรกของเทิร์นที่ห่างจากขั้นก่อนไม่เกิน 60 นาที มี 95 ครั้ง
ในนั้น **52 ครั้งอ่าน cache ได้ 0** และต้องเขียนใหม่รวม 3.71M โทเค็น คิดเป็นเงินที่เสียเกิน ≈ **$23.03**
ส่วนอีก 43 ครั้งอ่านได้ตามปกติ (34.5k–116.8k)
ตัวเลขนี้เป็นเพดานบน เพราะบางครั้งเป็นการสลับโปรเจกต์จริง ซึ่ง prompt ต้องเปลี่ยนอยู่แล้ว

**วิธีประหยัด**
- (1a) **ปลอดภัย ทำได้เลย** ย้าย `git status --short` ออกจาก system prompt ไปใส่ในข้อความ user ของเทิร์นนั้น
  ใช้วิธีเดียวกับที่ #92 ทำกับสกิล (`[Git status now …]` ต่อท้ายข้อความปัจจุบัน)
  โมเดลยังเห็น status ล่าสุดทุกเทิร์นเหมือนเดิม ไม่เสียข้อมูล และค่าใช้จ่ายเพิ่มแค่ไม่กี่สิบโทเค็นต่อเทิร์น
- (1b) **ปลอดภัย ทำได้เลย** เปลี่ยนบรรทัด LIVE STATUS ให้เหลือแค่ CONNECTED หรือ NOT CONNECTED ส่วนจำนวน tool และ error ล่าสุดย้ายไปไว้ในบล็อกของเทิร์น
  และเรียง Related projects ตามชื่อแทนลำดับที่เปิดล่าสุด
- (1c) **ให้เจ้าของตัดสินใจ** ล็อก PROJECT STRUCTURE และ CODEBASE MAP ไว้ตามตอนเริ่มแชท (Claude Code ก็ทำแบบนี้ โดยระบุไว้ว่าเป็น "snapshot")
  แล้วรีเฟรชเมื่อ open_project หรือเปิดแชทใหม่เท่านั้น
  ความเสี่ยงคือโมเดลไม่เห็นไฟล์ใหม่ใน tree แต่ไฟล์ที่โมเดลสร้างเองก็อยู่ในประวัติแล้ว และยังใช้ glob/list_files ได้
- (1d) **ทางเลือก** ใส่ breakpoint ที่ tool ตัวสุดท้าย เพื่อให้ tools (~12k+) ยังอยู่ใน cache เมื่อ system เปลี่ยน
  แต่ breakpoint นี้แย่งช่องที่ 4 กับข้อ 2 ถ้าทำ 1a–1c แล้ว ข้อนี้แทบไม่จำเป็น

**ประมาณการ**: ถ้าทำ 1a+1b ได้ $15–20 จาก $23 ถ้าทำ 1c ด้วยได้ใกล้ $23 ภายในช่วง 19 วันเดียวกัน
ถ้าแปลงเป็นต่อครั้ง เทิร์นที่ไม่ต้องเขียนใหม่จะประหยัด ≈ $0.30–0.80 ต่อเทิร์น บน Opus 5.5

**ความเสี่ยงต่องาน**: 1a และ 1b ต่ำมาก เพราะข้อมูลที่โมเดลเห็นเท่าเดิม แค่ย้ายตำแหน่ง ส่วน 1c ต่ำถึงกลาง

## 2. microcompact ขยับจุดตัด แล้วต้องเขียนบทสนทนาใหม่ทั้งหมด

**ที่พบ**: `CodeAgentService.cs:3880` / `:5459` (`NextCompactBoundary`) จะขยับจุดตัดไปที่ `Count−3` เมื่อบทสนทนาเกิน 90k (ค่าประมาณ, `:5394`)
ส่วนที่อยู่ก่อนจุดตัดเดิมยังเหมือนเดิมทุกไบต์ เพราะ `MicrocompactUpTo` ให้ผลเหมือนเดิมทุกครั้ง (deterministic)
แต่ breakpoint ของบทสนทนาอยู่แค่ที่ข้อความสุดท้ายและข้อความ user ก่อนหน้า (`AnthropicProvider.cs:521`)
ตำแหน่งที่เคยเขียน cache ไว้จึงตกอยู่ในช่วงที่เพิ่งถูกย่อทั้งหมด และ API ย้อนหาได้ไม่เกินประมาณ 20 block
ผลคืออ่าน cache ได้แค่ system+tools (≈36.8k ตรงกับ `cacheR=36774/37228/36782` ใน log) แล้วต้องเขียนส่วนที่เหลือ 105k–167k ใหม่

**ที่วัดได้**: เกิด 23 ครั้ง ต้องเขียนใหม่ 3.68M โทเค็น เงินที่เสียเกิน ≈ **$17.65**
ตัวอย่างหนัก: รอบวันที่ 10-28 เวลา 17:16 มี 186 ขั้น เกิด miss ที่ขั้น 47, 96, 136, 143, 164, 172, 178 และ 186

**วิธีประหยัด (ปลอดภัย ทำได้เลย)**: ใช้ breakpoint ช่องที่ 4 ที่ยังว่างอยู่ (system 1 + บทสนทนา 2 = 3 จาก 4 ช่อง)
วางไว้ที่ข้อความสุดท้ายก่อนจุดตัดของ microcompact ซึ่งเป็นส่วนที่ไม่เปลี่ยนจนกว่าจะถึงการขยับครั้งถัดไป
ในขั้นที่จุดตัดขยับ ให้คง breakpoint ไว้ที่จุดตัดเดิมอีก 1 ขั้น ส่วน prefix ที่ถูกย่อไปแล้วก็จะยังอ่านได้จาก cache
ข้อนี้ไม่เปลี่ยนสิ่งที่โมเดลเห็นเลย เปลี่ยนแค่ตำแหน่ง `cache_control`
(ข้อควรระวัง: ข้อ 3 ต้องไม่ไปเปลี่ยนข้อความก่อนจุดตัด ดูข้อ 3)
**ประมาณการ**: $7–12 จาก $17.65 ส่วนที่ยังต้องเขียนใหม่คือช่วงระหว่างจุดตัดเดิมกับจุดตัดใหม่
**ความเสี่ยงต่องาน**: ไม่มี ทดสอบได้แบบ offline ด้วย `tests/apitest` PromptCacheReuse และ mock

**ที่วัดได้**: เกิด 17 ครั้ง (เช่น ขั้น 101, 115, 133, 145, 165, 174, 187, 204, 211, 216 ของรอบวันที่ 10-29)

## 4. รอเกิน 5 นาทีกลางรอบ ทำให้ cache ของบทสนทนาหมดอายุ

**ที่พบ**: breakpoint ของบทสนทนาเป็น TTL 5 นาที (`AnthropicProvider.cs:524`) ส่วน prefix เป็น 1 ชั่วโมงแล้ว (`:875`)

**ที่วัดได้**: เกิด 9 ครั้ง เงินที่เสียเกิน ≈ **$5.12**
**ทางเลือก (ให้เจ้าของเลือก)**:
- (4a) ส่ง request ราคาถูก (`max_tokens=1`, prefix เดิม) ทุก ~4.5 นาทีระหว่างที่รันค้างรอผู้ใช้หรือรอ tool
  เพื่อต่ออายุ cache ค่าใช้จ่ายครั้งละประมาณ $0.03 (อ่าน 150k) เทียบกับการเขียนใหม่ $0.75
  แต่จะมีการใช้ API ในช่วงที่ไม่มีใครทำงาน
- (4b) **ไม่แนะนำ** ใช้ TTL 1 ชั่วโมงกับบทสนทนาด้วย วิธีนี้ทำให้เนื้อหาใหม่ทุกขั้นแพงขึ้น 0.75 เท่าของราคา input
  ประเมินแล้วจะเสียเพิ่มประมาณ $20 ต่อ 2,500 ขั้น มากกว่าที่ประหยัดได้
**ประมาณการ**: ไม่เกิน $4.8 ถ้าเลือก 4a
